# Learning standards

ENNTOR teaches learners to plan, write, test, repair and explain correct code independently in unfamiliar situations. The first Course Pack targets practical Python and applied AI/ML interviews. Give adult learners with prior knowledge a short path to doing the work. Establish prerequisites that matter for the objective and spend teaching time on mechanisms that make unfamiliar problems tractable.

The [curriculum v1.1](../Python_AI_Interview_Learning_Curriculum_v1.1.md) is a blueprint for 22 modules and 135 lessons, including placement. O00 establishes study practice and placement, F01–F06 build Python fluency, A01–A05 cover algorithms, D01–D03 introduce NumPy, linear algebra and pandas, S01–S02 cover math and statistics, M01–M03 put ML and AI into code, and I01–I02 cover live coding and timed mixed assessments. Read the exact lesson and its mentor notes, prerequisites and module gates. Exercise-bank counts, examples and assessment targets in the blueprint describe planned content. The runnable [Climb mini-unit](../review/milestone-4a/README.md) includes F01.01 through F01.03.

Use the [source ledger](REQUIREMENT_TRACEABILITY.md) for the status of specific rules. The [teaching guidelines](../teaching-guidelines.md) provide a short author checklist. The curriculum's [pedagogy references](../Python_AI_Interview_Learning_Curriculum_v1.1.md#14-pedagogy-and-design-research-separate-from-course-comparisons) inform PRIMM, worked-example fading, and plan → execute → check → reflect. These are design principles. Review their fit for adult interview preparation, the subject and the task. Added explanation can help a novice and burden an experienced learner. Balance unguided struggle and over-instruction by checking actual work.

## What counts as evidence

| Activity | Evidence it can provide |
| --- | --- |
| Recognition or explanation | Identifies the idea or can explain a mechanism, invariant or failure mode |
| Prediction and tracing | Anticipates behavior before execution and can account for intermediate state |
| Modify | Reads existing code and changes a specified behavior |
| Build | Turns a requirement into a partially scaffolded implementation |
| Make | Chooses and writes a fresh implementation from an explicit contract |
| Debugging | Uses an observed failure to investigate and repair an implementation |
| Transfer | Selects the skill again in a new problem or data shape with little or no guidance |
| Retention and timed assessment | Repeats the skill after a delay or demonstrates it under disclosed time and assistance rules |

Separate conceptual understanding, correctness and robustness, independence, efficiency/reasoning, retention and speed. Completion is a saved lifecycle outcome. Independent performance is an evidence claim tied to a specific task and assistance history. Module-level gates and timed readiness require broader evidence. Read the curriculum's §7 thresholds as operational heuristics, with multiple fresh tasks and checks, not a certification or hiring prediction. Teach untimed correctness first. Use about 15 minutes as a planning default, disclose a longer activity before entry, and offer a natural pause. Time spent checking code cannot measure focus or confidence.

## Teaching sequence

Use the following progression when it suits the objective. Merge or split stages deliberately in other subjects. Keep the evidence requirement explicit and use the least demanding scaffold that lets the learner take the next step.

1. **Why and Learn.** Tie the objective to a practical problem. Teach the mental model in plain language and define the minimum required vocabulary. Place relevant mentor notes near the idea they clarify. Introduce symbols in code or prose before referencing them, or clearly flag an upcoming example. A worked example should be executable and small enough to trace, explain why the approach satisfies the requirement, and include a meaningful boundary or counterexample. Keep output, narration and code in agreement.
2. **Predict and Run.** Require a committed prediction before revealing real output. Teach the general principle beforehand and reserve the specific trap for Investigate. Place a short outcome acknowledgment beside the actual result and explain the mechanism. Record runtime status separately. Give a tiny fresh follow-up when a wrong answer exposed a significant gap.
3. **Investigate.** Start at the result and trace dependencies backward, then execute forward, as in F01.01. Contrast possible and actual behavior explicitly. For the public F01.01 fixture, a prediction of 30 can come from grouping the sum before multiplication. Python prints 22 because multiplication takes precedence in that expression. Ask whether the grouping describes the learner's thinking and use the follow-up to check the concept in a different example.
4. **Modify.** Present working code that fails the *new* requirement and asks for a specific behavioral change. The learner reads the existing flow and edits a meaningful local part. Execution alone cannot satisfy the goal.
5. **Build.** Have the learner identify inputs, output and the relationship from a short requirement. Supply a partial declaration or skeleton, then ask for the core expression, branch or loop. Teach necessary syntax in context, such as an indented return in a function body. Reduce support across steps. F01.01 uses a seat-count plan and incomplete function before the independent receipt problem.
6. **Make.** Use an empty or comment-only editor. Ask for a full implementation in a fresh context with a precise contract. The learner chooses how to represent and compute the result. Remove guidance without simultaneously changing language syntax, data representation and algorithmic demands. Vary the structure or surface enough that copying Build cannot demonstrate transfer.
7. **Transfer and Finish.** Use a fresh problem or explanation check to test whether reasoning traveled. Require independent evidence after implementation or solution help where needed for the gate. Finish should preserve completed core work and supporting evidence, open a distinct report and offer the optional Sweat check-in. Use clear next actions for an unmet prerequisite and turn stretch gaps into optional practice where allowed.

Keep the Climb sequential with prior work revisitable. Adapt examples, scaffolding and variant difficulty inside the course path. For hard prerequisite failures, offer another explanation and an intermediate task. The scope of any future placement bypass remains [open](OPEN_DECISIONS.md). Significant new objectives can get an explicit bridge assessment while earlier completions retain their source version.

## Exercises and feedback

**Author the behavioral contract.** State intent, essential context, the meaning and units of inputs, per-unit versus total quantities, inclusion/exclusion, valid ranges, interface name and parameter order/types, return type and meaningful boundary cases. Work an example independently from the text, then compare it against the executable fixtures. Read the prompt for two reasonable interpretations. Remove story details that teach nothing and require no specialized domain knowledge unless the objective calls for it. For the warehouse practice, name both parts of the scale reading, say what a pallet count represents, and define the cargo-only result in kilograms. A zero-pallet case checks the interpretation. That domain contract leaves the Python expression open. Implementation instructions belong in guided stages or in a task that explicitly assesses the technique.

**Validate the assessment.** Run every authored snippet and example on the declared runtime and package versions. Confirm starters fail a required case, references pass, and likely wrong implementations fail discriminating tests. Cover valid boundaries such as zero, empty, negatives, duplicates, all-reserved or unusual shapes as appropriate. Specify precision and tolerances for numerical exercises. Check returns where the contract asks for returns. Keep content examples, worked solutions and grading fixtures distinct. Browser-delivered cases are public.

**Offer help at the right moment.** A conceptual nudge follows a meaningful failed check. Take one verified symptom and ask one diagnostic question with minimal implementation disclosure. Leave the editor quiet while the learner types or runs without asking for review. A requested hint is a separate form of assistance. Disclose one next action and keep revealed help readable. H0 reframes or asks a question, H1 points to a relevant relationship or invariant, H2 sketches a plan, H3 gives partial implementation, and H4 shows a complete worked explanation with a case that demonstrates why it works. Choose useful levels for the task and record the actual levels shown. H3/H4 are implementation or solution evidence. Give help on request without penalty for asking, and require a distinct fresh unaided task before claiming independent skill after implementation or solution exposure. An early instruction to put parentheses around the required sum gives away the decisive change.

**Diagnose the work.** Read actual source, provenance and graded cases. When justified, use parsed structure corroborated by behavior. Distinguish syntax/indentation, runtime exceptions, missing or wrong-type return, ordinary wrong values, a missed edge case, and a verified grouping or operand relationship. For a reverse-subtraction pattern in the warehouse fixture, use the actual failing zero-pallet case and ask what the cargo should weigh. Avoid providing replacement code as a first nudge. A wrong value alone cannot distinguish arithmetic confusion, misreading the contract and a coding mistake. Record the observable facts, a possible explanation if supported, and the learner's confirmation or rejection separately. If unsure, ask the learner what they intended or suggest tracing one case. Retain rejection and avoid repeating the same nudge. Reports may say the learner confirmed an explanation for one attempt without generalizing it to the person.

**Use evidence to train.** Give later corrections and independent transfer weight while preserving history. Limited evidence can justify optional reinforcement or an invitation to check a technique. A recurring misconception claim requires evidence across contexts; the historical roughly three-events/two-context rule is an initial heuristic. Warm-ups should be optional and independent of the main editor. Match upcoming Predict with theory and a tiny trace, Modify with a structure recap, Build with partial construction, and Make with theory plus an executable Modify exercise in a different scenario. Save opening, skipping, completing and revisiting where implemented. Warm-up work supports preparation and is not a Make result. Spaced retrieval, later in the roadmap, favors fresh application at roughly 1/3/7/14/30 days as an adjustable starting point.

**Record what happened.** Preserve lesson, task, content, runtime and grading versions, session and attempt identities, outcomes, help exposure, observations, hypotheses and responses, retries, corrections, timing scope and optional difficulty. Separate unassisted success, conceptual coaching, requested hints, implementation help, full solution exposure and subsequent unaided transfer. Record no response to Sweat as unanswered. Subjective challenge, behavior and strength of diagnostic evidence are different measures. See [report and survey behavior](UX_STANDARDS.md#reports-and-sweat).

## Review before release

Use a per-lesson manifest with the exact curriculum lesson ID, source and content versions, objective and observable evidence, assumed and newly introduced prerequisites, next-lesson continuity, concept introductions, examples and citations, authored activities and original fixtures, the hint levels disclosed and where solution help becomes available, suspected failure examples, transfer and completion rules, effort estimate, evidence history impact, automated results, synthetic UI evidence and reviewer/date. For a content batch, the independent reviewer compares the manifest and delivered sequence with the full authoritative curriculum, including objectives, dependencies and gates outside the batch. Use original prompts and paraphrase or cite external research rather than reproducing protected questions or employer tests.

Automate schema, stable ID and prerequisite graph checks, semantic references, output and precision checks, valid/invalid solutions, and evidence/reload regressions as contracts permit. Partial coverage and unsolved edge cases should be explicit. Novelty checks are prompts for editorial inspection. They cannot determine if a reskin teaches transfer. Independent editorial review is a separate checkpoint after Codex self-review. The independent reviewer reads the prose in the order delivered and runs representative tasks as a learner. Ask the product owner for selective hands-on testing of new teaching interactions, major navigation changes, and high-stakes or ambiguous learning flows. Routine instances of an approved pattern use independent sampling and synthetic evidence without requiring the owner to inspect screenshots for every lesson.

During editorial review, inspect what each hint reveals, whether Make is doable at that point in the course, and whether a reasonable alternate interpretation or correct implementation would be rejected.

Assess these dimensions separately: correctness, source alignment, teaching clarity, scaffold gradient, independent transfer, assignment precision, help and feedback, assessment validity, evidence honesty, and retention/cumulative use. Use examples and severity. A suggested 0–4 rubric and a 3/4 target for core dimensions is [a proposal](OPEN_DECISIONS.md#authoring-and-review-calibration). Any critical error, solution leak or false independence claim blocks release regardless of average. See [release gates](RELEASE_GATES.md).
